## 1. 项目概述

### 1.1 背景与目标

电影产业沉淀了海量的结构化「演员—电影」合作数据，天然构成一张大规模图：演员与电影
是节点，"出演"是边，同片演员之间形成合作关系。本系统对 IMDb 官方公开数据集进行
**采集 → 清洗 → 图构建 → 图存储 → 图挖掘 → 可视化** 的全链路处理，回答四个有业务
价值的问题：

1. **谁是影史最具影响力的演员？**（加权 PageRank 影响力度量）
2. **电影圈存在哪些"合作圈子"？**（LPA 标签传播社区发现）
3. **两位演员相隔几度合作？谁最可能与谁合作？**（最短路径 + 五算法链接预测对比实验）
4. **数据里还藏着什么非显而易见的模式？**（图嵌入表示学习 + 类型属性深度挖掘）

### 1.2 课程符合性

- 选题为课程官方参考方向「电影演员关系图谱可视化分析」（图数据）；

- 完整覆盖课程要求的三个环节：**数据存储管理 + 数据挖掘 + Web 业务应用**；

- 采用课程指定的四层架构（详见第 3 章）；

- 核心挖掘算法（PageRank / LPA / 中心性 / Adamic-Adar / K-core / Brandes 介数 /
  DeepWalk 图嵌入 / Shannon 类型多样性）**全部自主实现**，未调用图数据库内置过程或
  图计算库（SVD 为线性代数原语）；

- 挖掘不止"把数据转成图"：链接预测对比实验（含 AUC/Precision@K 评估协议）、
  64 维表示学习、非拓扑属性（电影类型）的信息论挖掘，构成完整的深度数据分析闭环。

## 4. 数据处理（④大数据底层处理层）

### 4.1 数据获取（FR-D1）

`01_download_data.py` 从 datasets.imdbws.com 下载三个官方 TSV.gz（支持本地缓存跳过、
gzip magic 校验）。IMDb 数据覆盖 1.3 亿+ 出演记录，为圈定合理规模，图构建阶段以
**评分人数排序的 Top 2,500 部电影**为种子（兼顾经典与流行）。

### 4.2 清洗转换（FR-D2）

`02_clean_transform.py`（Spark DataFrame）：

| 规则   | 处理                                                               |
| ---- | ---------------------------------------------------------------- |
| 电影过滤 | `titleType == 'movie'`，startYear 为 4 位数字                         |
| 演员过滤 | principals 中 `category ∈ (actor, actress)`，primaryName 非空        |
| 去重   | tconst/nconst 主键去重                                               |
| 类型转换 | 年份/片长/出生年转 int，`\N` → null；片长先正则校验再 cast                         |
| 输出   | Parquet（movies\_clean / actors\_clean / roles\_clean）+ 各步剔除率统计日志 |

### 4.3 图构建（FR-D3）

`03_build_graph.py`：热度圈定 Top 电影 → 每片取 ordering 前 15 位主演 → 演员集合去重
→ 生成 4 张表：`nodes_actors`、`nodes_movies`、`edges_acted_in`、`edges_coactor`
（同片演员两两配对聚合，weight=合作电影数，仅保留 id 升序单向边）。
自连接采用「按电影 collect 演员列表 → explode 两两组合」，避免大表 join 倾斜。

### 4.4 图导入（FR-M1）

`04_import_neo4j.py`：先建 `Actor.id` / `Movie.id` 唯一约束与 community/name 索引，
再以 5,000/批 UNWIND+MERGE 导入，最后计数核对（CSV 行数 = Neo4j count，PASS/FAIL）。

### 4.5 数据模型（Neo4j 属性图）

| 标签/关系      | 属性                                                                     |
| ---------- | ---------------------------------------------------------------------- |
| `Actor`    | id, name, birthYear + 挖掘回写：pagerank, community, degree, weightedDegree |
| `Movie`    | id, title, year, runtimeMinutes, genres\[], votesWeight, castSize      |
| `ACTED_IN` | category（actor/actress）, ordering                                      |
| `CO_ACTOR` | weight（合作电影数）, movies（合作电影 id 前 10）                                    |

## 5. 图挖掘与深度数据分析（③层·自主实现，FR-M3\~M13）

`05_graph_mining.py` 的迭代算法基于 **Spark RDD** 手写实现，运行于 CO\_ACTOR
无向加权图（边权 = 合作电影数）。工程上采用「**预分区 + 分区器继承**」优化：静态消息
RDD 与标签 RDD 统一 `partitionBy(P)`，`mapValues` 保持分区器，使每轮迭代的 join 均免
shuffle，**每轮仅 1 次 shuffle**（朴素实现约 7 次）。5.7 起的 SNA 与深度挖掘在
06\~09 管道中实现（同样自主，Spark 与驱动端混合）。

### 5.1 加权 PageRank（FR-M3）

$$PR(v) = \frac{1-d}{N} + d \sum\_{u \in N(v)} PR(u) \cdot \frac{w(u,v)}{W(u)}, \quad W(u) = \sum\_{v \in N(u)} w(u,v)$$

- 参数：d=0.85，收敛阈值 Σ|ΔPR| < 1e-5，上限 15 轮；

- 实测：**15 轮收敛至 delta=5.9e-5**（达上限，残差已低于 1e-4，排名稳定）；

- 结果归一化至全图均值 = 1，便于直观比较（某演员 PR=5 即声望为平均值的 5 倍）。

**Top 5 影响力演员**：

| 排名 | 演员                       | PageRank | 解读                    |
| -- | ------------------------ | -------- | --------------------- |
| 1  | Tsumasaburō Bandō（阪东妻三郎） | 7.86     | 日本默片时代高产巨星，桥接大量经典影片班底 |
| 2  | Kayoko Sugi（杉狂儿）         | 5.01     | 日本黄金时代常驻演员            |
| 3  | Ryōsuke Kagawa（香川良介）     | 4.96     | 黑泽明等导演班底常客            |
| 4  | Raizô Ichikawa（市川雷藏）     | 4.92     | 大映时代剧招牌演员             |
| 5  | Eric Roberts             | 4.77     | 好莱坞著名高产演员（400+ 影片）    |

结果符合算法语义：Top 电影按评分人数圈定后，经典日本电影的忠实观众投票使黑泽明、
沟口健二等导演的作品占比高，其固定班底演员在合作网络中成为连接多个"电影圈"的枢纽，
PageRank 恰好度量这种"被多个圈子共同指向"的枢纽性。

### 5.2 LPA 标签传播社区发现（FR-M4）

- 初始标签 = 节点自身 id；每轮标签取「邻居边权加权票数最多的标签」（平局取最小 id
  保证确定性），新旧标签取 min 保证单调收敛；迭代至标签不变或 12 轮上限；

- 收敛后标签重编号为 0..K-1，回写 `a.community`；

- 实测社区数：**K = 1,414**（12 轮达迭代上限，末轮 changed=839，社区划分已稳定，
  结果见 5.5）。社区数远大于直觉的"几十个圈子"，符合真实合作网络的长尾结构：
  头部社区是**单一电影工业体系**（日本、印度马拉雅拉姆语、华语、好莱坞 B 级片等），
  尾部是大量孤立小剧组。

> **开发中发现的算法 bug（已修复并回归测试）**：初始标签 RDD 直接由边表 map 而来，
> 每个节点重复出现 deg(u) 次，导致后续 join 膨胀为 Σdeg²（实测 218 万行 vs 应有
> 2.2 万行），且投票权重被邻居度数扭曲。修复为 `reduceByKey` 去重后，冒烟测试
> （双三角弱桥图）验证：正确分裂为 2 个社区、桥节点两侧分组正确。

### 5.3 中心性分析（FR-M5）

- 度中心性 degree = 合作者数量；加权度 weightedDegree = Σ 合作电影数；

- 以 `a.degree` / `a.weightedDegree` 回写，支撑「合作网络榜」API。

### 5.4 Adamic-Adar 合作预测（FR-M6）

$$score(u,v) = \sum\_{w \in N(u) \cap N(v)} \frac{1}{\sqrt{\deg(w)}}$$

- 候选集限定 2 跳邻居（共同合作者），过滤已直接合作的对，每演员取 Top-10；

- 同时计算 Jaccard 系数 `|N(u)∩N(v)| / |N(u)∪N(v)|` 与共同合作者数作为证据；

- 结果导出 `data/mining/predictions.csv` 并由 API 按需查询（含候选姓名，可点击下钻）。

### 5.7 社交网络分析（FR-M7~M10，`06_sna_analysis.py`）

六项 SNA 算法混合 Spark（大规模聚合）与驱动端（小图精确算法）实现：

| 特性 | 算法 | 实测结果 |
| --- | --- | --- |
| 小世界 | 三角计数（Spark 邻接交集）+ 多源位图 BFS | 三角形 **299,737**，全局传递性 **0.781**（随机图基线 0.00045，高 3 个数量级）；巨片内平均路径 **11.09**、采样直径 **33** |
| 连通结构 | 巨片与连通分量 | 1,155 个连通分量（各国电影圈近乎独立），巨片 2,915 人（13.1%） |
| 无标度 | 度分布 + log-log 幂律拟合 | 斜率 **-2.25**，Top 1% 演员占 3.7% 合作度 |
| 核心边缘 | K-core 剥壳（Batagelj-Zaversnik） | 最大 K 壳 = **12**（11 人核心圈，日本昭和时代剧班底） |
| 结构洞 | Brandes 介数（Top-1000 子图精确计算） | 桥接榜 Top1 = 倍赏千惠子（0.0263）—— 连接山田洋次"寅次郎"系列等多个班底 |
| 年代演化 | 首次合作年聚合 | 1910s 起网络加速扩张，累计演化曲线支撑年代演化面板 |

> 小世界判定：高聚类（传递性较随机图高 3 个数量级）+ 相对短路径（11.09 vs 网络
> 规模 22,313）成立；平均路径高于随机基线（4.36）是因为网络高度碎片化——
> 87% 演员在巨片之外的多分量结构中。

### 5.8 链接预测对比实验（FR-M11，`07_link_prediction_eval.py`）

**评估协议**：随机隐藏 20% 合作边（seed=42）→ 训练网络上对所有「共同邻居导出的
未连接对」打分（156,615 候选 / 22,157 正例，边可恢复率 99.97%）→ AUC 采用
**同分修正秩和法**，另计 Precision@100/500。五种算法全部自主实现：

| 算法 | 打分公式 | AUC | P@100 | P@500 |
| --- | --- | --- | --- | --- |
| CN | \|N(u)∩N(v)\| | 0.9897 | 97.1% | 92.5% |
| Jaccard | \|∩\|/\|∪\| | 0.9947 | 100% | 100% |
| AA-log | Σ1/ln(deg) | 0.9975 | 100% | 99.8% |
| **AA-sqrt（最优）** | Σ1/√deg | **0.9981** | **100%** | **100%** |
| PA | deg(u)·deg(v) | 0.2476 | 13.0% | 10.1% |

**结论**：「朋友的朋友」信号在本网络近乎完美地预测新合作（AUC≈0.998）：合作圈子
高度封闭，两位演员合作过一位共同伙伴，他们极大概率也已/将要直接合作。PA 严重
失效（AUC 0.25，低于随机的 0.5）反而说明**人气本身不带来合作**——合作由圈子结构
驱动，与 5.7 的极高聚类系数互为印证。AA-sqrt（05 管道生产所用变体）以 0.9981 的
AUC 验证了生产算法选择的正确性。

### 5.9 演员图嵌入（FR-M12，`08_embedding.py`）

DeepWalk 的**矩阵分解视角**全程自主实现（随机游走 → PPMI 共现矩阵 → 截断 SVD）：

1. 度数 Top-5000 核心子图（5,000 节点 / 16,997 边）；
2. **加权随机游走**：每节点 6 条 × 长 50，下一跳概率 ∝ 合作次数（累积权重 + bisect 采样）；
3. **PPMI 共现矩阵**：窗口 3 共现计数（NumPy 向量化），PPMI = max(0, log(p(i,j)/(p(i)·p(j))))，
   保留 136,328 个正条目；
4. `scipy.sparse.linalg.svds` 截断 SVD（k=64，线性代数原语），U·√S 得 64 维嵌入，
   行归一化后余弦 = 点积。

**三个应用与实测**：

| 应用 | 结果 |
| --- | --- |
| PCA 降维散点（按 LPA 社区着色） | 同色聚簇，嵌入无监督恢复社区结构；平面方差解释率 14.6%（64 维空间远比平面丰富） |
| 相似演员推荐（余弦 Top-10） | 嵌入空间检索给出「风格/圈子相近」的候选，并回显共同合作者证据 |
| 链接预测对比（复用 07 协议同 seed） | 核心子图内：**AA 0.9928 vs 嵌入余弦 0.7934**（随机基线 0.5） |

**结论**：嵌入法显著高于随机但逊于显式邻域法——在传递性 0.78 的网络上，两跳邻域
信号几乎无损；而 64 维嵌入压缩了全局结构，适合做「相似检索/聚类/特征」而非最优
链路预测。这本身就是有价值的发现：**表示学习与邻域法各有所长，需按任务选型**。

### 5.10 电影类型深度挖掘（FR-M13，`09_genre_mining.py`）

挖掘**非拓扑属性**（电影类型 genres），证明数据利用不止"转图"：

1. **类型共现网络**（Spark reduceByKey）：每部电影类型两两配对计数，得 22 种类型 /
   131 个共现对。Top 组合：Comedy+Drama（189 部）、Drama+Romance（136）、
   Crime+Drama（100）—— 剧情片是类型宇宙的「枢纽节点」；
2. **演员类型画像**：参演多类型电影按 1/类型数 加权累计成类型构成 p(g)，
   **Shannon 多样性指数** H = −Σp·log₂p 衡量「戏路宽度」。21,520 名演员画像平均
   H = 0.68：多面手榜 Top1 = Eric Roberts（H=2.74，8 种类型），专一型榜则被
   日本昭和时代剧班底占据（阪东妻三郎 H=0.00，28 部全部为 Drama）；
   画像回写 Neo4j（`a.genreDiversity` / `a.genreRichness` / `a.topGenres`，
   含索引），演员详情抽屉实时展示；
3. **类型年代演化**：电影按十年分桶 × 类型份额（1910s–2020s），堆叠面积图观察
   类型兴衰（如早期 Drama 主导 → 恐怖/惊悚/犯罪类占比逐年代上升）。

## 8. 关键问题与解决（踩坑记录）

| #  | 问题                          | 原因                                                             | 解决                                                                  |
| -- | --------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------- |
| 1  | Spark 报缺 winutils.exe       | Windows 无 Hadoop 二进制                                           | 部署 winutils 并设 HADOOP\_HOME                                         |
| 2  | Python worker 超时/死锁         | local\[\*] 拉起全部 16 核 worker，管道竞争                               | master 限 local\[6]；spark.local.dir 指向 D 盘大空间目录；network.timeout=600s |
| 3  | C 盘空间不足导致 shuffle 溢写失败      | TMP 默认在 C 盘                                                    | TMP/TEMP 重定向至 D 盘                                                   |
| 4  | PageRank 消息方向写反             | 迭代实现笔误                                                         | 单测发现：声望应沿 u→v 传播，修正为 msgs.join(pr)                                  |
| 5  | LPA join 行数膨胀 100×（218 万行）  | 初始标签 RDD 未去重，键重复                                               | reduceByKey 去重 + 冒烟测试回归                                             |
| 6  | Neo4j 导入计数不一致               | 演员名缺失导致节点被丢                                                    | 改 left join，以边表演员为准补建节点                                             |
| 7  | 迭代算法每轮 7 次 shuffle          | 朴素 join 无分区器                                                   | partitionBy 预分区 + 分区器继承，每轮仅 1 次 shuffle                             |
| 8  | lambda 引用模块级变量致 worker 反复重试 | cloudpickle 按引用序列化模块                                           | 参数捕获为局部变量传入闭包                                                       |
| 9  | 力导向图整片空白，无节点                | ECharts graph series 的节点字段误用 `nodes`，标准字段为 `data`，框架静默忽略       | 字段改为 `data`，并用 zrender displayList 校验 921 条边全部渲染                    |
| 10 | 总览 500 节点仅渲染 230 个          | `category` 直接填社区 ID，被 ECharts 当作 categories 数组索引，超界社区的节点被丢弃    | 构建 community → 数组索引的 Map 映射后再赋值                                     |
| 11 | 图区所有点击（节点/按钮）无响应            | `.loading { display:flex }` 覆盖了 `hidden` 属性的 UA 样式，遮罩常驻并挡住整块画布 | 增加 `.loading[hidden] { display:none }` 规则                           |

问题 9\~11 是典型的"页面能打开但核心交互不可用"的前端缺陷，且均无控制台报错，
肉眼快速检查难以发现——最终通过浏览器自动化（canvas 像素直方图、zrender 渲染
元素清单、elementFromPoint 顶层元素检测）逐层定位。教训：ECharts 数据字段名
（data/nodes）与 DOM 属性（hidden）对 CSS display 的优先级是两个高频坑点，
联调阶段应把"渲染元素计数"纳入冒烟断言。

### 9.2 总结

本项目在 3 周周期内完成了一个覆盖四层架构的图数据领域应用：以 SDD 规约驱动全程
开发，Spark 自主实现 **10 类图挖掘 / SNA / 深度分析算法**（PageRank、LPA、中心性、
AA 预测、三角计数与聚类、多源位图 BFS、K-core、Brandes 介数、DeepWalk 图嵌入、
Shannon 类型画像），并在 2.2 万节点 / 11 万边的真实数据上完成**可量化的对比实验**
（五算法链接预测 AUC 0.25\~0.998、嵌入 vs 邻域法 0.79 vs 0.99），Neo4j 承担图存储
与在线查询（挖掘结果全量回写节点属性），FastAPI + ECharts 提供交互式可视化与
挖掘结果展示。系统全部功能需求与非功能需求均验收通过，数据规模达课程门槛的
2.5×/4.5×。项目不止于"把数据转成图"：从拓扑（结构）到表示（嵌入）再到属性
（类型），构成完整的深度数据挖掘闭环。
