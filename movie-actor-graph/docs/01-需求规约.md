## 1. 项目背景与目标

### 1.1 背景

电影产业沉淀了海量结构化的「演员—电影」合作数据。这些数据天然构成一张大规模图
（Graph）：演员与电影作为节点，"出演"作为边，两位演员若共同出演同一部电影则在合作
网络中产生关联。基于该图可以回答一系列有业务价值的问题：谁是影史最具影响力的演员？
电影圈存在哪些"合作圈子"（社区）？两位演员之间通过几部电影可以建立联系（六度分隔）？

### 1.2 项目目标

构建一个覆盖**大数据底层处理 → 图数据管理与挖掘 → Web 业务应用**完整链路的
领域应用系统，对电影演员合作关系进行存储、挖掘与交互式可视化分析。

### 1.3 课程符合性声明（对照课程说明第 8/10 页）

- ✅ 选题为课程官方参考方向之一："电影演员关系图谱可视化分析"（图数据）；
- ✅ 题目同时覆盖课程要求的三个环节：**数据存储管理 + 数据挖掘 + Web 业务应用**；
- ✅ 非纯增删改查系统：包含 PageRank、社区发现、中心性分析等图挖掘功能；
- ✅ 采用课程指定的四层架构（详见《02-设计规约》第 3 章）。

## 2. 用户与场景

### 2.1 目标用户

| 用户角色 | 使用场景 |
|---|---|
| 影迷 / 普通用户 | 浏览演员合作关系、查找两位演员的合作路径、查看演员详情 |
| 数据分析人员 | 研究演员影响力排名、合作社区结构、演员合作网络演化 |
| 课程评审 / 答辩教师 | 验证四层架构的完整性与各层设计决策 |

### 2.2 核心业务场景

1. **图谱浏览**：打开系统即看到演员合作网络总览（含社区着色），可拖拽、缩放、点选。
2. **演员检索**：按姓名（支持中文名与英文名）搜索演员，定位其在网络中的位置。
3. **关系探索**：点击任一演员，展示其主演电影与主要合作者；下钻查看合作电影详情。
4. **合作路径查询**：输入两位演员，计算并可视化他们在合作网络中的最短路径（"几度合作"）。
5. **影响力排行**：查看按 PageRank / 度中心性 / 合作强度排序的演员影响力榜单。
6. **社区发现**：查看算法挖掘出的"合作圈子"（如某导演班底、某类型片常用班底）。
7. **合作预测**：基于共同合作者数量等图特征，推荐某演员最可能尚未合作的演员。

## 3. 功能需求（FR）

功能按四层架构归属编号：FR-D*（数据管道/底层处理）、FR-M*（数据管理与挖掘）、
FR-B*（业务逻辑层）、FR-U*（交互层）。

### 3.1 数据获取与底层处理（对应④大数据底层处理层）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-D1 | 从公开数据集（IMDb 官方公开数据集 datasets.imdbws.com）获取原始数据：演员表、电影基础信息、演员-电影出演表 | 必须 | 原始 TSV 数据落盘到 `data/raw/`，字段完整可解析 |
| FR-D2 | 使用 Spark 进行分布式数据清洗：过滤非电影类型、去重、缺失值处理、类型转换 | 必须 | 清洗后数据无重复主键、关键字段（演员ID/电影ID/名称）无空值 |
| FR-D3 | 构建图数据集：生成演员节点表、电影节点表、出演关系边表、演员合作边表 | 必须 | 输出规模达到课程门槛：**节点 ≥ 10,000，关系边 ≥ 30,000** |
| FR-D4 | 数据管道支持增量运行与统计报告（各阶段数据量、剔除率） | 应该 | 每次运行输出处理统计日志 |

### 3.2 图数据管理与挖掘（对应③数据管理与挖掘层）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-M1 | 图数据导入 Neo4j 属性图数据库，建立索引与约束 | 必须 | 节点/边数量与 Spark 输出一致；ID 唯一性约束生效 |
| FR-M2 | 支持 Cypher 图查询：邻居查询、多跳关系查询、路径查询 | 必须 | API 响应时间 ≤ 2s（2 跳内查询） |
| FR-M3 | PageRank 演员影响力计算（**基于 Spark 自主实现迭代算法**，非直接调用图数据库内置过程） | 必须 | 输出全量演员 PageRank 分值并回写图数据库节点属性 |
| FR-M4 | 社区发现（标签传播算法 LPA，**Spark 自主实现**），挖掘合作"圈子" | 必须 | 每个演员获得社区编号，回写图数据库，支持按社区过滤 |
| FR-M5 | 中心性分析：度中心性、加权合作强度排名 | 必须 | 提供排行榜 API |
| FR-M6 | 合作预测：基于共同邻居（Jaccard/共同合作者数）的演员合作推荐 | 应该 | 给定演员返回 Top-N 潜在合作者及共同合作者证据 |
| FR-M7 | 小世界特性分析：三角计数与全局/局部聚类系数、多源 BFS 采样平均路径长度与直径估计（"六度分隔"验证） | 应该 | 输出网络级指标；平均路径基于 ≥63 个采样源 |
| FR-M8 | 介数中心性（Brandes 算法，核心子图精确计算），识别社区间"桥接演员"（结构洞） | 应该 | 输出介数榜单，含归一化分值 |
| FR-M9 | K-core 核心边缘结构分解（Batagelj-Zaversnik 剥壳），识别最紧密合作核心圈 | 应该 | 每个演员获得 kshell/core 属性并回写 |
| FR-M10 | 合作网络年代演化分析：每年新增合作关系数、新增演员数及累计增长 | 应该 | 输出按年的演化序列 CSV |
| FR-M11 | 链接预测对比实验：随机隐藏 20% 合作边为测试集，在训练图上用共同邻居 CN / Jaccard / Adamic-Adar（标准 1/log 与生产 1/√ 变体）/ 优先连接 PA 五种算法为候选对打分，评估 AUC 与 Precision@K | 应该 | 输出各算法 AUC / P@K 与最可靠的新合作预测样例；AUC 显著高于 0.5 随机基线 |
| FR-M12 | 演员图嵌入（表示学习，自主实现 DeepWalk 矩阵分解视角）：在度数 Top-5000 核心子图上加权随机游走，构建窗口共现 PPMI 矩阵后截断 SVD 得 64 维演员嵌入；提供嵌入空间降维可视化（颜色=社区）、基于余弦相似度的相似演员推荐、以及嵌入法 vs 邻域法（Adamic-Adar）的链接预测 AUC 对比 | 应该 | 输出嵌入 CSV 与对比 JSON；嵌入法 AUC 与 AA 可比 |
| FR-M13 | 电影类型深度挖掘：类型共现网络（同片类型对计数）、演员类型画像（Shannon 多样性指数 + 类型构成）、类型构成的年代演化（按十年类型份额） | 应该 | 输出类型共现/画像/演化 CSV；多面手演员榜可查 |

## 5. 数据需求

### 5.1 数据源

IMDb 官方公开数据集（https://datasets.imdbws.com/，非商业授权，课程允许的"公开数据集"渠道）：

| 文件 | 内容 | 用途 |
|---|---|---|
| `name.basics.tsv.gz` | 人员基础信息（nconst、姓名、职业、生卒年） | 演员节点属性 |
| `title.basics.tsv.gz` | 作品基础信息（tconst、类型、年份、片长） | 电影节点属性、过滤"电影"类型 |
| `title.principals.tsv.gz` | 作品主要演职员表（tconst、nconst、职务 category） | "出演"关系边 |

### 5.2 目标图模型（概要，详细见设计规约）

- 节点：`Actor`（演员）、`Movie`（电影）
- 边：`ACTED_IN`（演员→电影，属性：角色职务、排序）
- 派生合作网络：`CO_ACTOR`（演员↔演员，属性：合作电影数、合作电影列表）

### 5.3 规模目标

以"高热度电影及其演员"为圈定策略（评分人数 ≥ 阈值的电影），保证：

- 演员节点 ≥ 8,000，电影节点 ≥ 2,000，合计节点 ≥ 10,000；
- `ACTED_IN` + `CO_ACTOR` 关系边合计 ≥ 30,000，其中 `CO_ACTOR` ≥ 15,000。

## 6. 约束与边界

### 6.1 技术约束（课程指定）

- 图数据库必须使用 **Neo4j**（课程③层图数据标准选型）；
- 底层处理须使用 **Spark**（课程④层标准组件），单机 local 模式运行，架构上保留集群扩展能力；
- 业务层使用 **Python + FastAPI**（课程②层允许的选型）；
- 交互层使用 **JavaScript + ECharts**（课程①层推荐组件）；
- 挖掘算法（PageRank、LPA、中心性、合作预测）须**自主实现**于 Spark 之上（评分导向："自主算法优于调库"）。

### 6.2 范围外（Out of Scope）

- 不做用户注册/登录与权限体系（非课程考察点）；
- 不做实时流处理（Flink 仅在架构文档中说明选型理由，不落地）；
- 不做票房/评分预测等超出图挖掘范围的主题模型；
- 前端不引入 Node 构建链（保持静态文件直发，降低环境复杂度）。
