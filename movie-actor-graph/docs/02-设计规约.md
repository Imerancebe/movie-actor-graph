## 2. 数据模型设计

### 2.1 属性图模型（Neo4j）

**节点标签**

| 标签 | 属性 | 类型 | 来源 |
|---|---|---|---|
| `Actor` | `id`（如 nm0000138） | String，唯一约束 | name.basics.nconst |
| | `name` | String | primaryName |
| | `birthYear` | Integer | birthYear（缺失置 null） |
| | `pagerank` | Float | 挖掘回写 |
| | `community` | Integer | 挖掘回写（LPA） |
| | `degree` | Integer | 挖掘回写（合作者数） |
| `Movie` | `id`（如 tt0111161） | String，唯一约束 | title.basics.tconst |
| | `title` | String | primaryTitle |
| | `year` | Integer | startYear |
| | `runtimeMinutes` | Integer | runtimeMinutes |
| | `genres` | String[] | genres 拆分 |
| | `votesWeight` | Integer | 圈定热度用的评分人数 |

**关系类型**

| 关系 | 方向 | 属性 | 语义 |
|---|---|---|---|
| `ACTED_IN` | Actor → Movie | `category`（actor/actress）、`ordering` | 演员出演电影 |
| `CO_ACTOR` | Actor → Actor（无向语义，存储单向） | `weight`（合作电影数）、`movies`（合作电影 id 列表截断至 10） | 两位演员合作网络 |

**索引与约束**

```cypher
CREATE CONSTRAINT actor_id IF NOT EXISTS FOR (a:Actor) REQUIRE a.id IS UNIQUE;
CREATE CONSTRAINT movie_id IF NOT EXISTS FOR (m:Movie) REQUIRE m.id IS UNIQUE;
CREATE INDEX actor_name IF NOT EXISTS FOR (a:Actor) ON (a.name);
CREATE INDEX actor_community IF NOT EXISTS FOR (a:Actor) ON (a.community);
```

理由：`id` 唯一约束保证导入幂等（MERGE 依据）；`name` 索引支撑搜索 API（FR-B5，500ms）；`community` 索引支撑社区过滤查询（FR-U5）。

### 2.2 中间数据格式（Spark 侧）

- 清洗后数据统一存 **Parquet**（列存、带 schema、压缩），作为③步输入；
- 图数据导出 **CSV**（`data/processed/graph/`），并附 `_stats.json` 记录节点/边数量，供导入程序核对与验收；
- 挖掘结果同时回写 Neo4j 与导出 `data/mining/*.csv`（榜单/社区/预测），供报告与前端兜底展示。

### 2.3 数据圈定策略（达到 NFR-1 规模）

IMDb 全量约 1.4 千万作品/1.4 千万人，必须圈定子集：

1. `title.basics` 过滤 `titleType == 'movie'` 且年份有效；
2. 以评分人数（`votesWeight`，来自 title.ratings 或代理热度字段）降序取 **Top 2,500 部电影**；
3. 取这些电影的 `title.principals` 中 `category ∈ {actor, actress}` 的出演记录；
4. 由出演记录反推演员集合（保证无孤立演员节点）；
5. 节点数 = 演员 + 电影，边数 = ACTED_IN + CO_ACTOR。

> 预期量级：Top 2500 电影 × 平均 ~15 主演 ≈ 3~4 万条出演边；演员约 1.5~2.5 万；
> CO_ACTOR = 同片演员两两组合去重（`C(n,2)` 截断，单片合作对上限内不截断整体），
> 预计 ≥ 10 万对，远超 3 万门槛。参数（TOP_MOVIES、MIN_VOTES）集中在管道配置中可调。
>
> **实测规模（2026-09-01 首次全量运行）**：选定电影 2,500 部；演员节点 22,313；
> ACTED_IN 边 25,000；CO_ACTOR 边 110,822；合计节点 24,813、边 135,822，
> 平均合作度 9.93 —— 节点为课程门槛（10,000）的 2.5 倍，边为门槛（30,000）的 4.5 倍。

## 3. 算法设计（自主实现，运行于 Spark）

### 3.1 PageRank（演员影响力）

- **模型**：把合作网络 `CO_ACTOR` 视为无向图，边权 = 合作电影数；
  迭代式 PageRank：`PR(v) = (1-d)/N + d × Σ_{u∈N(v)} PR(u)·w(u,v)/W(u)`，
  其中 `W(u) = Σ_{v∈N(u)} w(u,v)` 为邻居边权之和，d=0.85。
- **实现**：RDD `join` + `reduceByKey` 迭代（预分区 + 分区器继承，每轮仅 1 次 shuffle），
  收敛条件 `Σ|ΔPR| < 1e-5` 或 15 轮上限。
- **选型理由**：影响力评估是图挖掘的基础必做项；无向加权 PageRank 符合"合作关系"
  语义（合作越多传递的声望越高）。

### 3.2 社区发现：标签传播 LPA

- **模型**：初始每个节点标签 = 自身 id；每轮节点标签取「邻居边权加权出现次数最多
  的标签」（并列取最小 id 保证确定性）；新旧标签取 min 保证单调收敛；迭代至标签
  不再变化或 12 轮上限。
- **实现**：RDD map 邻居消息 → reduceByKey 聚合投票 → join 回标签表；
  收敛后将原始标签映射为连续社区编号（0..K-1）。
- **选型理由**：LPA 复杂度近线性，适合 10 万级边；相比 Louvain 实现简单且可解释，
  适合课设周期与答辩讲解。

### 3.3 中心性与榜单

- 度中心性：`CO_ACTOR` 邻居计数（加权度 = 合作对总权重）；
- 多产演员：`ACTED_IN` 出边计数；
- 热门电影：`ACTED_IN` 入边计数（演员阵容规模）。

### 3.4 合作预测（共同邻居 + Jaccard）

- 对目标演员的「合作者的合作者」打分：
  `score(u,v) = Σ_{w∈N(u)∩N(v)} 1/sqrt(deg(w))`（Adamic-Adar），
  并计算 `Jaccard = |N(u)∩N(v)| / |N(u)∪N(v)|`；
- 过滤已有合作关系，输出 Top-N 及共同合作者姓名列表（作为推荐证据）。
- **选型理由**：链路预测是图挖掘的经典任务，Adamic-Adar 优于纯共同邻居数，
  体现算法设计深度；结果可解释（给出共同合作者），适合前端展示。

### 3.5 挖掘结果回写

Spark 产出 `(actorId, pagerank)`、`(actorId, community)`、`(actorId, degree)` 与预测表，
统一通过驱动端分批 `UNWIND ... SET` 写回 Neo4j（每批 5,000，避免单事务过大）。

### 3.6 社交网络分析（SNA）扩展算法（06_sna_analysis.py，FR-M7~M10）

**① 三角计数与聚类系数（Spark）**：邻接表广播（2.2 万节点 × 平均度 10，约几 MB），
每条边求共同邻居数 `|N(u)∩N(v)|`（单遍 map）；三角总数 `T = Σc/3`；
节点级 `tri(u) = ½Σ_{v∈N(u)} c(u,v)`；局部聚类系数 `2·tri(u)/(deg(u)(deg(u)-1))`；
全局传递性 `3T / Σ deg(deg-1)/2`。

**② 多源 BFS 平均路径（Spark，位图并行）**：从**巨片（最大连通分量）**随机抽取
63 个源节点（种子固定可复现）。实测合作网络含 1,155 个连通分量（各国电影圈近乎
独立成簇，巨片仅占 13%、2,915 人），跨分量不存在路径，若在全图随机采样，平均路径
会被大量平均仅 ~17 人的小分量主导而失真——故小世界指标在巨片上度量（网络科学的
标准做法）。每节点维护 63 位整数掩码标记已到达的源；每轮迭代沿边传播掩码按位 OR，
本轮新增的位数即"该距离上的点对数"，得到距离直方图 → 采样平均路径长度与直径估计。
一次 Spark 作业同时完成全部 63 个源的 BFS（相比逐源 BFS 快 63 倍）。
节点级输出采样接近中心性 `closeness(v) = |S_v| / Σ_s dist(s,v)`。

**③ K-core 剥壳（驱动端，Batagelj-Zaversnik）**：小根堆按当前度数依次移除节点，
移除时的度即核心数 core；`kshell = core`。22K 节点/110K 边在驱动端内存中瞬时完成
（图规模 << 内存，无需分布式）。

**④ Brandes 介数中心性（驱动端，核心子图精确计算）**：取度数 Top-N（默认 1000）
演员的诱导子图，在其上运行精确 Brandes（BFS + 依赖反向传播），
归一化 `2·BC(v)/((n-1)(n-2))`。选择核心子图的原因：全图精确介数需 22K 次 BFS，
Spark 逐源作业开销不可行；Top-1000 核心子图恰为 K-core 分析的"核心圈"，
桥接演员几乎必然位于其中。

**⑤ 度分布与幂律（Spark）**：`reduceByKey` 聚合度数直方图，导出 (度数, 人数)；
配合头部节点度数占比（Top 1% 节点的度数份额）验证无标度特性，前端 log-log 呈现。

**⑥ 年代演化（Spark）**：`edges_acted_in` 按电影分组 → 组内演员两两配对并携带电影年份，
`reduceByKey min` 得每对演员的**首次合作年份**；同样方式得每位演员的**出道年份**；
按年聚合输出新增合作边数/新增演员数及累计曲线（约 26 万个配对实例，规模可控）。

**实测结论（2026-09-04 运行）**：三角 299,737、全局传递性 0.781（随机图基线 0.00045，
约 1,750 倍）、平均局部聚类 0.957；巨片内 63 源采样平均路径 11.09、直径 33——路径与
随机图基线 4.36 同数量级但仍偏长，根因是巨片呈"国家影圈链"结构（K-core 核心圈 11 人
全部为日本默片时代演员，介数 Top-10 亦以日本影人为主，度数榜另有斯里兰卡群像片演员）；
K 壳最大 12；度分布幂律斜率 -2.254、Top-1% 度数份额 3.7%（长尾无标度成立但重尾较缓，
且度 9 处存在 20,523 人的尖峰——「每片取前 10 位主演」规则下单片演员恰有 9 位同片
合作者，属数据产物而非网络结构特征）；
年代演化累计合作对 110,822，与 CO_ACTOR 边总数精确一致（交叉验证通过）。

### 3.7 链接预测对比实验（07_link_prediction_eval.py，FR-M11）

把 FR-M6 的单一 Adamic-Adar 预测升级为**可评估的对比实验**：

**协议（随机隐藏边 / 网络补全）**：固定种子随机抽取 20% CO_ACTOR 边为测试集并从图中
移除，剩余 80% 构成训练图。候选对 = 训练图中**存在 ≥1 个共同邻居**且**非训练边**的
节点对（邻域类算法的适用域；测试边中无共同邻居者不可恢复，单独统计其占比）。
测试集边落入候选集者为正样本，其余候选对为负样本。

**五种打分算法**（均在训练图上计算，N(u) 为训练图邻居集）：

| 算法 | 公式 | 说明 |
|---|---|---|
| CN | \|N(u)∩N(v)\| | 共同邻居数，最朴素基线 |
| Jaccard | \|N(u)∩N(v)\| / \|N(u)∪N(v)\| | 归一化共同邻居 |
| AA（标准） | Σ_{w∈N(u)∩N(v)} 1/ln(deg(w)) | 抑制高度数共同邻居的经典形式 |
| AA（√变体） | Σ_{w∈N(u)∩N(v)} 1/√deg(w) | 05 生产预测器所用变体，实验顺带验证其有效性 |
| PA | deg(u)·deg(v) | 优先连接（富者愈富），与邻域无关的基线 |

**评估指标**：
- **AUC** = P(随机正样本得分 > 随机负样本得分) + ½·P(相等)，按同分修正的秩和法
  计算（Spark 按 score 分桶聚合 (桶大小, 正样本数) 后驱动端遍历，避免全量 collect）；
- **Precision@K**（K=100/500）：得分 Top-K 候选对中正样本占比。

**执行位置**：候选对生成（共同邻居两两配对）与打分在 Spark（广播训练图邻接表，
与 06 三角计数同模式）；数据划分与指标计算在驱动端。产出
`data/mining/prediction_eval.json`（五算法 AUC/P@K、协议统计、最优算法 Top-10
新合作预测样例含姓名与共同合作者证据）。

### 3.8 演员图嵌入（08_embedding.py，FR-M12，自主实现表示学习）

把图结构转化为演员向量（DeepWalk 的矩阵分解视角，全部自主实现）：

1. **核心子图**：全图按度数取 Top-5000 演员的诱导子图（与 Brandes 的 Top-1000 先例
   同理：嵌入的语义在核心结构上最有意义，且 5000×5000 共现矩阵可稠密分解）；
2. **加权随机游走**：每节点 6 条 × 长 50，下一跳概率 ∝ 合作次数（边权），
   `bisect` + 累积权重采样（游走偏好重合作关系，等价于以合作强度为转移核）；
3. **PPMI 共现矩阵**：窗口 3 内的共现对计数（NumPy 向量化：游走数组按偏移切片后
   `a*5000+b` 编码 + `np.unique` 聚合，避免 Python 逐对循环），
   计算 PPMI = max(0, log( p(i,j) / (p(i)·p(j)) ))；
4. **截断 SVD**：`scipy.sparse.linalg.svds(k=64)` 分解 PPMI 矩阵，U·√S 得 64 维嵌入，
   行归一化后余弦相似度 = 点积（SVD 为线性代数原语，算法设计——游走/PPMI/分解
   目标——均为自主实现）。

**三个应用**：
- **降维可视化**：嵌入 PCA（NumPy SVD）投影到 2D，按度数采样 2,000 点，
  颜色 = LPA 社区（嵌入是否自发恢复社区结构是质量检验）；
- **相似演员推荐**：单位化嵌入的余弦最近邻 Top-10（附共同合作者数作交叉证据）；
- **嵌入法 vs 邻域法链接预测对比**：复用 07 的划分协议（同 seed 42、同候选集），
   嵌入余弦为第六种打分（子图外候选对得 0 分，另报核心子图内 AUC），
   回答"学到的向量能否替代显式邻域计算"。

产出：`actor_embeddings.csv`（5000×64）、`embedding_scatter.csv`、
`embedding_neighbors.csv`（每人 Top-10）、`embedding_summary.json`（含对比 AUC）。

### 3.9 电影类型深度挖掘（09_genre_mining.py，FR-M13，Spark）

挖掘**非拓扑属性**（电影类型 genres），证明数据利用不止"转图"：

1. **类型共现网络**：每部电影的类型两两配对（如 Adventure+Drama）计数，
   reduceByKey 聚合 → 类型节点 + 共现加权边（19 个类型的小网络，力导向可视化）；
2. **演员类型画像**：edges_acted_in join 电影类型 → 每演员的类型构成分布
   p(g)，**Shannon 多样性指数** H = -Σ p·log₂p + 丰富度（类型数）+ Top-3 类型，
   回写 Neo4j（a.genreDiversity / a.genreRichness / a.topGenres）；
   "多面手演员"（高 H）与"专一型演员"（低 H）形成画像光谱；
3. **类型年代演化**：电影按十年分桶 × 类型计数 → 各年代类型份额矩阵，
   观察类型兴衰（堆叠面积图可视化）。

产出：`genre_cooccurrence.csv`、`actor_genre_profiles.csv`、`genre_era_evolution.csv`。

## 4. 接口设计

统一响应包裹：

```json
{ "code": 0, "msg": "ok", "data": { } }
```

错误码：0 成功；400 参数错误；404 资源不存在；500 内部错误。

主要接口（与需求 3.5 清单一一对应）：

| 接口 | 关键查询（Neo4j） | 说明 |
|---|---|---|
| `GET /api/stats` | `CALL apoc.meta.stats` 替代方案：count 聚合 | 节点/边/社区数/平均度 |
| `GET /api/graph/overview?limit=` | Actor 按 pagerank 降序取核心节点 + 其 CO_ACTOR 边 | 首屏力导向图数据 |
| `GET /api/actor/search?name=` | `WHERE toLower(a.name) STARTS WITH / CONTAINS $kw`（前缀优先排序；Neo4j RE2J 正则不支持 `(?i)` 内联标志，故用 toLower 方案） | 限 20 条 |
| `GET /api/actor/{id}/neighbors` | 一跳 CO_ACTOR + ACTED_IN→Movie | 详情面板 |
| `GET /api/actor/{id}/detail` | 节点属性 + 度数 + 社区 + 代表作品 | 详情面板头部 |
| `GET /api/path?from=&to=` | `MATCH p = shortestPath((a)-[:CO_ACTOR*..6]-(b))` | 合作路径 |
| `GET /api/rank/pagerank` | `ORDER BY a.pagerank DESC LIMIT n` | 榜单 |
| `GET /api/rank/degree` | `ORDER BY a.degree DESC` / Movie 入度 | 榜单 |
| `GET /api/communities` | `GROUP BY community` 聚合（规模、Top 成员） | 社区面板 |
| `GET /api/community/{id}/members` | `WHERE community = $id` | 社区成员 |
| `GET /api/predict/{id}` | 读 Spark 预测结果（mining CSV 已回写/读缓存） | 合作预测 |
| `GET /api/sna/metrics` | 读 `sna_summary.json`（聚类系数/平均路径/直径/密度/巨片） | 小世界指标 |
| `GET /api/sna/degree-distribution` | 读 `degree_distribution.csv` | log-log 度分布 |
| `GET /api/sna/evolution` | 读 `evolution.csv` | 年代演化曲线 |
| `GET /api/sna/kcore` | Neo4j `GROUP BY kshell` + 核心圈成员 | K-core 结构 |
| `GET /api/sna/prediction-eval` | 读 `prediction_eval.json` | 链接预测对比实验 |
| `GET /api/sna/embeddings` | 读 `embedding_scatter.csv` + `embedding_summary.json` | 嵌入空间可视化 |
| `GET /api/actor/{id}/similar` | 读 `embedding_neighbors.csv` | 相似演员推荐 |
| `GET /api/sna/genres` | 读类型挖掘三个 CSV | 类型挖掘 |
| `GET /api/rank/betweenness` | `ORDER BY a.betweenness DESC`（核心子图节点） | 桥接演员榜 |
| `GET /api/health` | 驱动 ping | 健康检查 |

**跨域与静态托管**：FastAPI 挂 `StaticFiles` 直发 `frontend/`，开发期无需独立前端服务器，
也避免 CORS 配置；保留 CORSMiddleware 以备前后端分离部署。

### 5.1 页面结构（单页应用，原生 JS）

```

│ · 社区列表     │                                          │
│ · 合作路径查询  ├──────────────────────────────────────────┤
│   (双选下拉)   │  右侧抽屉：演员详情                        │
```

### 5.2 可视化映射规则

| 数据维度 | 视觉通道 |
|---|---|
| 演员影响力 pagerank | 节点直径（对数缩放 8~46px） |
| 社区编号 | 节点颜色（20 色调色板循环） |
| 合作次数 weight | 边透明度/粗细 |
| 电影年份 | 详情面板列表排序键 |

### 5.3 交互细节

- 图数据懒加载：首屏 `overview` 只取 Top 影响力子图（默认 ≤ 500 节点）保证流畅（FR-U1）；
- 点击节点 → 右抽屉详情 + 邻域高亮（其余节点降透明度）；
- 路径查询结果 → 视图切换到路径子图，节点带序号标签；
- 社区点击 → 图谱过滤为该社区核心子图；
- 搜索 → 下拉联想（防抖 300ms），回车定位并展开邻域。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| IMDb 原始文件大（principals ~600MB）下载/处理慢 | 下载脚本支持断点与本地缓存跳过；Spark 只读取必需列 |
| Windows 本地 Spark 环境问题（winutils/HADOOP_HOME） | 使用 PySpark 3.x + 指定 `spark.sql.warehouse.dir` 到项目内路径；README 记录排障 |
| CO_ACTOR 边爆炸（单片演员多导致组合数大） | 圈定主演（principals.ordering ≤ 15）限制单片演员数；权重聚合去重 |
| 力导向图节点过多卡顿 | overview 采样 + 前端 layoutAnimation 关闭大数据集 |
| 导入幂等 | 唯一约束 + MERGE/批量导入前清库校验 |
